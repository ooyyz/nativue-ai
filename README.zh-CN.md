# Nativue AI

**Your canvas for AI-native development.**

[English](README.md) · 简体中文

开发仓库：[ooyyz/nativue-ai](https://github.com/ooyyz/nativue-ai)。

**给非代码背景的 vibe coder，一张掌控复杂软件开发的工作画布。**

当你用 AI 开发一个架构复杂、面向生产的软件项目，功能越来越多，模块相互牵连，多个 Agent 同时工作，难题也会从“让它写出来”变成：**我怎么掌握全局，确认它没改偏，还能高效推进？**

Nativue 把架构图、用户流程和并行开发进度放在一起。你继续用自然语言做产品决策，通过图看清模块关系、讨论改动范围，让 AI 按确认后的方向开发，再用 A/B/C 分工和独立验收把进度管起来。它帮助你管理代码背后的项目，无需先逐行读懂实现。

发行团队：**SienGe AI Lab** · 小红书：**SienGe的AI实验室**

## 起点：项目越做越大，怎么才能不失控？

Nativue 源于作者在小红书分享的 AI 开发经历，以下按场景整理：

> 我没有代码背景，却在用 AI 开发一个结构复杂、以生产级软件为目标的项目。开发越往后，越容易遇到 Agent 理解不准、反复返工、进度难以掌握的问题。
>
> 作为 Figma 流程图的深度用户，我先让 AI 搭了一个代码架构画布：能看清每个模块在做什么、它们怎么通信、一个用户流程会经过哪些模块。这样和 AI 讨论时，我有一张能对照的全局地图。
>
> 然后我把 Agent 分成 A、B、C：A 和我讨论交互、拆分任务；B 专心开发，可以按边界分几路并行；C 独立验收，不通过就交回 B 返工。集成后的版本再复验，最后由我手测把关。

这就是 Nativue 想支持的工作方式：**用架构图掌控全局，让 AI 开发有范围；用清晰分工和并行视图，管理复杂项目的开发进度。** 架构图帮助你提出具体问题、检查变化是否符合预期；独立验收与最后的用户判断继续保留。

如果你的项目正从一个简单原型，走向多模块、多轮迭代、需要组合验收的长期开发，这套方式尤其有用。

## 本地开始

### 第一次使用：安装并创建画布

当前是源码安装候选版，无需 npm 正式发布或云端部署。安装 **Node.js 24 及以上**和 Git，在克隆后的 Nativue 目录运行：

```sh
npm install
npm run build
node bin/nativue.js init /path/to/workspace
node bin/nativue.js serve /path/to/workspace
```

打开 `serve` 输出的本地地址。初始化选择语言、AI 工具、协作模式、角色模型、扫描范围，以及是否开启远端同步。先索引实际文件，再由 Agent 提供带源码证据的架构解释；目录分组不代表架构已经验证。

可以把这句话交给 Agent：

> 读取当前 Nativue 仓库的 `skills/nativue/SKILL.md`。为我选择的工作区初始化，先读取开发规范，再生成第一版架构分析。如果发现多个仓库，先让我选择范围，然后打开画布。

通过 `node bin/nativue.js --help` 查看 `install-skill` 的安装参数，也可以直接加载 Skill 入口。它独立于项目已有规范，不覆盖原有指令文件。

### 再次打开：继续使用已有画布

**关闭网页、退出服务或关机后，不需要从头生成画布。** 已有架构、任务和配置保存在所选工作区的 `.nativue/` 目录中。

- **只关闭了网页，服务仍在运行**：在原来的浏览器中重新打开服务地址，默认是 <http://127.0.0.1:4317>。
- **关闭了终端、停止了服务或重启了电脑**：打开终端，进入之前克隆的 Nativue 目录，只运行：

  ```sh
  node bin/nativue.js serve /path/to/workspace
  ```

  将 `/path/to/workspace` 替换为**之前初始化的同一个工作区路径**，再打开命令输出的地址。保留这个终端运行；按 `Ctrl+C` 会停止服务。已有安装无需重复执行 `npm install`、`npm run build` 或 `init`。

服务启动时会检查源码变化，读取已有画布，并按当前源码更新文件索引和已启用的 Java 建图；源码发生变化时，画布内容可能随之更新。

架构图的节点位置、缩放和折叠状态保存在**浏览器的本地存储**中。恢复布局时，请使用原来的浏览器及用户配置、同一个工作区路径和相同地址（包括端口）；`localhost` 与 `127.0.0.1` 也属于不同地址。如果之前指定了端口，重启时沿用 `--port 原端口号`。更换浏览器、清除网站数据或关闭无痕窗口后，布局可能无法恢复，但工作区 `.nativue/` 中的画布数据仍保留。

也可以直接告诉 Agent：

> 为之前的工作区启动 Nativue 服务，打开已有画布，沿用原来的地址和端口，不要重新初始化。

模块按前端、后端、应用服务和基础设施分组。连线说明模块如何关联，右侧可以继续查看任务、模块职责与源码证据；画布支持拖动、缩放和折叠。

## 两种协作方式

| 模式     | 使用方式                             | 适用场景          |
|--------|----------------------------------|---------------|
| 独立对话   | 自己打开 A、B、C，用带版本的任务交接包接续          | 兼容更多工具，需要细致把控 |
| A 自动调度 | A 使用宿主提供的子 Agent 能力创建独立的 B/C 上下文 | 单批任务较多、可并行开发  |

**A** 确认需求、拆分和协调；**B** 开发、自测及返工；**C** 独立验收 B 提交的准确版本。单项通过后集成，再由 C 验收集成版本，最后交给用户手测。C 不能代用户签署通过。

模型按角色由用户配置；Nativue 无法自行切换当前对话模型，也不把某个工具的子 Agent 接口当成其他工具的接口。详见[协作流程](docs/workflow.md)。

## Java 源码自动建图

运行 `node bin/nativue.js configure-java /path/to/workspace --scope src` 启用本地解析；加 `--parent moduleId` 挂到已有主模块。`--config rules.json` 支持 `enabled`、`roots`、可选 `parentId` 和功能入口规则（`id`、`name`、`seeds`）。规则只定义功能入口，类、方法和关系自动提取；省略规则时按源码声明与关系推导候选功能。

可从功能进入类、方法和两跳调用链。继承、实现、注解注入、构造参数依赖及方法调用保留源码位置；歧义或缺失目标列为诊断。文件监听复用未变化的语法事实，自动更新关系并展示新增、变化和删除项，各层布局跨刷新保存。静态声明目标不代表运行时派发。详见[范围、解析规则与限制](docs/java-architecture.md)。

功能内部的类画布按源码层级排列：同一功能下的接口与实现类、父类与子类组成一组，内部类和枚举缩进显示，并标明所属类型。箭头表示实现或继承等源码关系，无箭头括线表示内部类型归属；详情中的“代码层级”可跳转到相关类型，包括其他功能中的类型。已有手动布局继续保留，点击“按代码层级排列”可重新整理当前功能，不影响其他层级保存的位置。分组依据源码声明，不根据 `Impl` 等名称猜测关系，也不改变功能归属。

类、方法前的 Javadoc、块注释和连续行注释会自动填充职责说明，并保留注释行号。没有功能规则时，短注释摘要用于推断功能名称；类或方法可选的 `@feature 名称`、`功能：名称` 标记能提供更明确的归属。点击“它负责什么”旁的“编辑”保存手动说明，重新分析和重启后仍保留；“恢复自动内容”切回最新源码说明。修改单独保存在工作区忽略目录 `.nativue/descriptions.json`，本地与远端版本分别保存。

功能详情支持“重命名”，类详情支持“调整归属”，可移动到同一架构下的其他功能。类的方法一并移动，当前层级的连线随新归属展示。名称与归属独立保存在 `.nativue/architecture-edits.json`，重新分析后保留，并可分别“恢复自动识别”。目标功能在源码中消失时，保留原设置并提示暂用自动归属；目标重新出现后恢复应用。

## 自动更新

`serve` 运行时持续检查文件和任务变化，网页关闭后仍可继续；服务进程退出即停止，不安装系统常驻任务。连续修改会合并处理，分析失败保留上一有效图，并显示待分析或已过期。

语义分析通过用户明确启用的命令适配器执行；`configure-runner codex` 或 `configure-runner claude` 可配置随附的宿主 CLI 桥接，使用你的账户及模型额度。Codex 桥接已有一次真实虚构仓库测试记录，Claude 桥接尚未实测。没有适配器时生成分析包，交给交互式 Agent 处理。刷新文件索引不会被标为架构分析完成。更新间隔和每日调用上限可配置，详见[运行与分析](docs/operation.md)。

远端同步在初始化时**自行选择开启**。本候选版支持公开的 GitHub HTTPS 来源，暂不支持需要认证的私有远端同步；本地私有仓库仍可正常扫描。工具在独立缓存中分析选定分支，不对工作区执行 pull、切分支或合并，也不会公开生成的图。没有 GitHub 也能使用本地任务。`issues` 将公开仓库未关闭的 Issue 导入为待办，识别 P0/P1/P2 标签，其他默认 P2；暂未实现自定义标签映射。远端评论、Issue 关闭、Push 和发布需要相应授权。

## 本地数据与隐私

状态、日志、缓存和本地配置存于 `.nativue/`，应始终排除在 Git 之外。扫描默认排除常见依赖、构建产物、凭证和运行数据；请检查是否符合你的项目。初始化不执行目标仓库的脚本，也不通过符号链接读取选定范围之外的文件。Agent 或命令适配器可能按配置将代码发往模型服务，适用该服务的数据设置；Nativue 本身不提供云端上传服务。

反馈问题请使用虚构示例。参见[贡献说明](CONTRIBUTING.md)、[发行检查](docs/RELEASE.md)及 [MIT 许可](LICENSE)。
